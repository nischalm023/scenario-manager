Worldview: the recording of a warehouse run, and how it streams

One file per run attempt: everything the run was built from, everything it did, and everything it ended with, seekable by simulated time. This document describes the file, how the simulator writes it, and how the Crucible server stores it and serves it to viewers.

Status: built on this branch, with an exact-parity check against the current master — cell-identical workbooks and byte-identical render arrays on four fixtures. The Crucible server and the browser viewer are built here too (docs/designs/crucible-server-ui.html). The simulator writes a recording at the END of a run; writing one while a run executes, and watching it, is not here — section 04 says what it waits on. The fleet of runner processes is a later initiative.

00 · what a worldview is

A run is a sequence of frames, written as it happens, read from any instant

A .worldview file holds everything one attempt of a run produced: the world it ran in, the scenario it ran, and the run itself as a time-indexed sequence of frames. It replaces the whole-run document that was written only when a run finished. Three properties drive the shape:

  • Appended, never rewritten. Frames are added in the order the run settles them, and nothing goes back over one. A file cut short is read to its last whole frame, and a reader can follow a file that is still growing — which is what a producer writing during a run would need, and no producer does that yet.
  • Seekable by simulated time. Keyframes restate the whole state at regular instants; deltas carry the changes between them. Any instant is one keyframe plus a bounded number of deltas away.
  • Self-contained. The scenario block at the front carries the world document, the scenario and its data, the configuration, and the tables that tie the run's compact identifiers to the world. Nothing outside the file is needed to replay it or to inspect it.

The same frames that go into the file go over the wire, in the same vocabulary: a browser attached to a run receives that file's own frames, each one possibly re-encoded with the sections it did not ask for removed. One format to write, one to read, one to test.

01 · the file

Scenario, then keyframes and deltas, then the index and the end

The file: what is written to disk and uploaded to storage

This is the durable form of a run: the file headless desvis writes, the object the Crucible server uploads when a run ends, and what desvis, the browser and the workbook all open afterwards. Every block below is a frame.

The stream: what a viewer receives when it attaches at an instant

This is the wire form: the same frames, sent over a websocket to a viewer opening a recorded run at a chosen instant. The server chooses where to start and what to leave out; the viewer decodes what it is sent and carries the state forward itself.

Every block is a frame: a fixed 20-byte header followed by a compressed payload. The header says what kind of frame it is, the simulated instant it starts at, how long the payload is, and a checksum over both. A reader walks a file or a stream twenty bytes at a time and decodes only the frames it needs.

BytesFieldMeaning
0tag (u8)the kind of frame: scenario, declare, keyframe, delta, index, end
1flags (u8)bit 0: the payload is zstd-compressed; the rest reserved
2–3reserved (u16)zero
4–11t_ms (u64)the simulated instant the frame's contents begin at, in milliseconds
12–15payload_len (u32)compressed payload length
16–19crc32c (u32)over the header's first sixteen bytes and the payload

Payloads are MessagePack, positional, compressed with zstd frame by frame, so a single frame can be read without touching its neighbours and the file can be tailed while it is written. A keyframe or delta payload opens with a section table, one entry per section it carries with its byte range, so a consumer decompresses once and keeps only the sections it wants.

02 · sections and what a frame says

One keyframe is the whole state, one delta is a slice's changes, and both are made of sections

A keyframe restates everything at an instant: where every robot and tote is, every metric's value, the visit grid. A delta states what one ten-second slice changed. Both are divided into sections, one per kind of state, declared by name in the scenario block; the section table at the front of the payload says where each lies, so a viewer that draws only the floor keeps the playback section and drops the rest without decoding it.

SectionIn a keyframeIn a delta
playbackevery robot (id, class, its x/y/z millimetres, heading, what it carries, the cell it is in and the one it is heading to), every tote (id, container type, designation, location, contents), the conveyor journeys under wayper closed slice: each mover's step list (where the step left it, how long it took, what kind of motion, the cell it arrived in) and the cell the slice leaves it in; tote births, moves, journeys and contents; relay reservations; station depths
scalarseach declared metric's reading (a gauge) or running sum (a counter), one position per descriptorthe slice's values, positional
heatthe cumulative visit grid per robot classthe slice's increments
tables—per declared table (robot legs, lift cycles, picks, …): the rows whose instants fall in the closed slice

The other frame kinds carry facts about the run or the file rather than state, and have no sections: the scenario block, a declaration of a table or metric that appears mid-run, the index, and the end block with the stop reason and the summary.

Identifiers. Frames name cells, robots, totes and stations by the compact integer ids the run uses (u32 values, which MessagePack writes in one to five bytes), because a step list of small ids is what keeps a delta at about two kilobytes. The scenario block carries the tables that tie those ids to the world: the world-protocol entity id of every cell and station, and each robot's name and class. Totes are created during a run, so a tote's identity is declared in the delta of the slice that creates it. Robots and totes are not entities of the world graph; they are the actors that move through it, and the world graph stays the static description of the site.

Places. A robot's place is its coordinates: whole millimetres along x, y and z in the world document's root 3-D frame, which the scenario block names once. Cells ride beside them and place nothing — they say which cell a consumer reporting per cell should count the robot against. Movement inside a slice is the straight line between two stated positions; the file's own numbers are whole millimetres, and what a viewer draws between two of them is the viewer's business. A tote's place stays symbolic: where a tote is drawn follows from what holds it, so a tote names a rack slot, a relay, a conveyor landmark or the robot carrying it.

03 · seeking and scrubbing

Nearest preceding keyframe, then the deltas forward

Slices are ten simulated seconds. A keyframe is written for slice zero and then every thirty slices, five simulated minutes. To show instant t, a reader finds the last keyframe at or before t, restates the state from it, and applies the deltas up to t: at most twenty-nine of them. Scrubbing backward inside the frames a viewer already holds is free; scrubbing to an instant it does not hold means asking for the preceding keyframe and playing forward.

Where the keyframes are is the index: one fixed-size record per frame (offset, instant, tag, length). The writer builds it in memory as it writes and puts it into the recording itself as the keyframe index block (one record per frame, keyframes and deltas alike, so a seek can find both), followed by the end block and a fixed-size trailer that says where the index block starts. Nothing of the index is written beside the recording. A reader that opens a file with no index block — one still being written, or one cut short — rebuilds it by scanning the headers, twenty bytes per frame, because every frame states its own length and checksum.

04 · how the simulator writes it

The observer's closed slices become frames

The simulator's SimObserver collects what a run does: where every robot and tote is at each slice, the metric values, the visit grid, and the per-run tables. Today it hands all of that over at the end of the run as one document. With worldview it becomes a frame producer.

What this branch does. At the end of the run, the observer's collected state is written as frames: the scenario block, then a keyframe at every boundary and a delta for every slice carrying that slice's table rows, the index and the end. The content is exactly what the whole-run document held, which is what makes an exact comparison against the current master possible (section 07). Headless desvis and the Crucible server both write this way, through the same function, so one spec run by either yields the same run — everything but the wall clock the run took, which the end block states and which no two runs share.

Planned: writing while the run executes. The simulator's only present is the scheduler's trailing global barrier — the instant behind which nothing more will be scheduled. Frames would be emitted only for the time buckets the barrier has already passed, out of an accumulator kept ahead of it, and what is emitted would be final: nothing revisits a bucket. That rests on a rule the simulator does not keep today, that no event may be emitted with a timestamp behind the barrier, and on the observer no longer filling closed slices in afterwards, which it does today from six places. The work is on its own branch, agent/worldview-emit, and none of it is in this one: no live writer, no provisional values, nothing a viewer would have to re-read. The format is ready for it — frames are appended and a reader can follow a growing file — and the server and the browser already speak of a live edge.

Either way the producer writes through one writer that refuses out-of-order frames, keeps the index it is building, and completes the recording with the index and end blocks.

05 · how the Crucible server tees it

One storage object per attempt, and the same frames to every viewer

A run executes inside the Crucible server process, on a worker thread. Dispatching runs across a fleet of separate runner processes is deferred to its own initiative. When the run ends the server writes its recording, uploads it to storage as one object — the attempt's only artifact — and drops the local copy.

  • One object per attempt, under runs/<run>/attempts/<n>/recording.worldview, in a local folder in development or a bucket in deployment, behind one interface.
  • Fetched back to be read. The first attachment to a run brings the object onto the server's machine, into a temporary folder bounded by a configured size; every later reader of that run finds the copy already there, with the compiled floor beside it.
  • One reader per attachment. Each browser gets its own reader over that copy, so a slow browser slows only itself; one that stops accepting frames for longer than the reader waits is dropped and told where to resume.

The wire from simulated time N is the file's own blocks in a viewer's order: the scenario block, filtered to what a browser needs (the world document, yes; the scenario's data files, no); the index up to that instant, so the viewer knows the run's extent at once; the one keyframe at or before N; every delta after it; and the end. No later keyframe travels: the viewer holds the state and carries it forward, and a viewer that falls behind is re-attached from a fresh keyframe. The server also filters sections, so a viewer drawing only the floor need not receive the tables.

06 · time series for the charts

Assembled by the server up to the attach instant, extended live by the client

The scalars section is small: a keyframe is tens of bytes and a delta about a hundred, so ten simulated hours are a few hundred kilobytes. When a viewer attaches at N and asks for charts, the server reads the scalars family from the recording's start to N using the index, extracts the requested metrics, and sends one consolidated reply, one point per slice, bucketed by averaging when the slice count exceeds what a chart can show. From then on the client appends each scalars delta as it arrives. The client never has to hold or replay the playback section to draw a chart.

07 · consumers, and the parity check

desvis, the workbook, and later the browser, all read the one recording

  • desvis plays a recording back, draws the floor from the world document in the scenario block, and reads the tables and metrics for its panels; its headless mode writes recordings.
  • workbook is the xlsx export, moved out of desvis into its own crate with a command of its own, so a spreadsheet can be produced from a recording anywhere.
  • The browser decodes the same frames with the same code compiled to WebAssembly, and draws them through the renderer desvis draws through.

Parity. The first cut is gated on exactness against the current master, measured on the same fixture and seed run by both binaries. Two checks: the workbooks must agree cell for cell; and desvis's per-tick render arrays, what it hands to the GPU at a fixed list of instants, must agree byte for byte. A twin run of one binary first proves the simulation deterministic, so a difference between binaries is a real difference. On the prototype branch, the workbook check was run by hand on cencora and DFW6 ten-minute runs and every cell agreed.

08 · measured on the prototype

What a recording costs: cencora measured, Walmart estimated

One hour of simulated cencora (the largest site in the fixtures, about nine thousand cells, a fleet of hundreds) on the prototype branch: 2.8 MB on disk, 2,604 frames. Thirteen playback keyframes of about 21 KB each; 362 playback deltas of about 2 KB each, one per ten-second slice; the same count of scalars and heat deltas; 1,442 table chunks; one scenario block of 44 KB carrying the world document and scenario. The prototype wrote one frame per family and one per table per slice; with sections, the same run is about 380 frames of the same total size. With release builds the simulator produced that hour in about sixty seconds of wall clock.

Walmart, estimated. The DFW6 site has about 170,000 storage slots and about 1.3 million units of inventory. A keyframe restates every container: id, type, designation, location and a unit count, about twelve to fourteen bytes each as positional MessagePack, so a Walmart keyframe is about 2.2 MB before compression. Every payload is zstd-compressed, and a sorted list of near-identical records compresses well; a three- to five-fold ratio would put a keyframe at 0.5 to 0.8 MB. Over a ten-hour run at the five-minute cadence that is 120 keyframes, 60 to 100 MB, with deltas small beside them; a browser attaching receives one keyframe, not 120, which is the case for sending only the starting keyframe on the wire. A per-tote unit count costs nothing extra for 1.3 million units; SKU-level contents per tote, if the entity inspector later wants them, would add on the order of a million entries per keyframe and belong in a table or behind a server query rather than in every keyframe. These are estimates with the assumptions stated. Measured in the format round (release build, ten simulated minutes, one thread): the DFW6 smoke fixture writes 418 KB in 27 frames; its one keyframe is 2,430,117 bytes decompressed and 174,976 bytes stored, a fourteen-fold ratio, because the census is dominated by near-identical container records; the scenario block is 143 KB (the world document and spec verbatim) and the median delta 3.3 KB. cencora writes 1.16 MB in 68 frames: keyframes 166,571 bytes decompressed and 40,905 stored, the median delta 15 KB, and the motion section (per-move speed profiles for the traffic overlay) is the largest part of a delta. Writing either file takes 0.03 s. A Walmart keyframe with 1.3 million units spread over real contents will compress less well than DFW6's empty census; the three- to five-fold figure stands as the planning number until a loaded fixture is measured. Two levers exist if the numbers bite: the keyframe cadence is a per-run value in the scenario block, and the container list can be written column-wise (all ids, then all locations, then all counts) so that zstd sees long runs of small differences.

10 · glossary

Five words this document leans on

  • Slice. Ten simulated seconds, the half-open interval from a start instant to the next; every delta describes one slice and is stamped with its start.
  • Section. A named part of a keyframe or delta (playback, scalars, heat, tables); a keyframe or delta opens with a table saying where each section lies.
  • Settled frontier (the barrier). The simulated instant behind which the simulator will change nothing; a slice closes, and can be written, only once the frontier has passed its end.
  • Live edge. The instant of the newest frame a recording holds; for a running simulation it advances as slices close.
  • Held window. The span of frames a viewer currently holds, from the keyframe it started at to the newest delta it has received; scrubbing inside it costs nothing, scrubbing outside it means a new attachment.
