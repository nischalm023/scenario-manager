Crucible: the websocket server and the browser UI

One server process runs simulations, records each as a .worldview, and serves a recording to browsers once the attempt that produced it has ended. The browser draws it with the same Rust renderer desvis uses, compiled to WebAssembly. This document describes the server, the protocol between it and a browser, the UI, and the rendering code the two viewers share.

Status: built on this branch, in the same pull request as the format. A run is submitted, queued, simulated inside the server, recorded, stored, and opened in a browser at any instant once its attempt has ended — finished, cancelled, or failed with something recorded. Watching a run while it executes is not here; section 06 says what it waits on. The split of the server into a broker and a fleet of runner processes, prototyped on agent/crucible-streaming, is out of scope and left to a later initiative; a run executes inside the server process, and PostgreSQL is the only container development needs.

00 · the shape

One process, three jobs: run, record, serve

Crucible was a single-process server, studio/runs, that ran one simulation and pushed its output to a browser over a websocket. This phase keeps that shape and changes what flows through it. Every run the server executes ends in a .worldview recording (the format is described in docs/designs/worldview-streaming.html), written from the finished run model, uploaded to storage, and served from there to every browser that asks for it. A browser opens a run at whatever instant it asks for, the first time or after a reload, and the server reads that instant out of the recording rather than replaying anything.

  • Run. A submitted specification becomes a run; the simulator executes it on a worker thread inside the server, up to a configured number of runs at once. There is one runner mode, in-process. Dispatching runs to separate runner processes is not part of this phase.
  • Record. When the run ends, its observer's collected state is written as one recording — by the same writer, from the same model, as when headless desvis runs that spec, so the two files hold the same run. The recording is uploaded whole to storage (a local folder in development, a Google Cloud Storage bucket in deployment, behind one interface) and the local copy dropped. The writer never sends to a browser, so no browser can slow the simulator or grow a queue in the server's memory.
  • Serve. Browsers speak one protocol over one websocket: submit, list, status, attach at an instant, detach, cancel, and a request for a metric's time series. Submitting a run returns its id and nothing else; watching is a separate attach, at 0 for the start or at N for a scrub or a re-attach, which reads the recording forward from that instant. Frames travel as binary messages; everything else is JSON text.

The run registry, which runs exist, their attempts and outcomes, and where their recordings are, lives in PostgreSQL, as it does in the prototype. It is the only external service, and dev.sh starts it in a container.

01 · the server

Runs execute inside it; a recording leaves it once, at the end

A submit carries the run's specification: the world document, the scenario and its data, the settings. The server checks the shape, stores the specification, creates the run and its first attempt in the registry, and queues the run; a worker thread picks it up when one is free and simulates it. When the run ends, the observer's collected state becomes the recording, written whole by the format's writer and uploaded to storage as the attempt's one object. Every browser attachment is then a reader of that recording: it seeks to the keyframe at or before the asked instant, sends what it finds, and walks the file forward from there, one delta per slice. A browser that reads slowly slows only its own reader; the server holds no per-browser queue beyond the websocket's own send buffer, and a browser that stops accepting frames for longer than the reader waits is dropped with lagged.

A run that ends in an orderly way — finished, cancelled by somebody, or stopped by the watchdog — is recorded from the model as it stands, so a cancelled run yields a shorter recording rather than a damaged one, and the recording carries the index block, the end block with the stop reason and the run's summary, and the trailer. The attempt's outcome and object key go to the registry. The other kind of ending is the server process itself dying mid-run: there is no recording to keep, because the file is written at the end, so at startup the server marks every attempt still marked running as partial, with nothing to open. A run whose simulator refused to continue is failed, with its reason, and is recorded not at all.

Every reader — a browser opening a run, a series reply, the floor compile, the workbook command on a downloaded file — reads that stored object. The first attachment to a run fetches the object onto the server's machine, into a temporary folder bounded by a configured size; later readers find the copy already there, and the runs nobody has read for longest are evicted whole.

02 · the protocol

Text to ask, binary to receive

The browser opens one websocket and holds one attachment at a time on it. Control messages are JSON objects tagged by type; frames are binary messages, each one frame of the recording as it stands in the file, so the same decoder reads the wire and the file.

Browser sendsServer answers
submit {spec}submitted {run}, before any work starts
list · status {run}list {runs} · status {run, attempts, progress}
attach {run, from: ms | "live", sections}attached {run, attempt, from_ms, live_edge_ms}, then the stream, read from the recording by this attachment's own reader: the scenario block filtered for a browser, the index up to the keyframe, the keyframe at or before from with the asked sections, then each delta after it, then the recording's end frame followed by ended {outcome}. "live" means the last instant the recording holds. Submitting a run returns no stream; the browser attaches once there is a recording.
detach · cancel {run}the stream stops · cancelled; the run stops where it is and is recorded from there
series {run, metrics, until}a JSON reply with each metric's points from the run's start to until, one per slice, bucketed only when there are more slices than a chart can show; afterwards the browser extends the series from the scalars section of each delta it receives. Binary messages stay worldview frames only; requests carry an id so replies and an attachment share the socket.
—lagged {resume_from_ms}: the browser's socket stopped accepting frames for longer than the reader will wait, so the attachment was dropped; the browser re-attaches at that instant, discards the state it held, and receives a fresh keyframe

Two things the server does on the browser's behalf. It filters: the scenario block a browser receives carries the world document, the id tables and every declaration made before the attach instant, but not the scenario's data files, and a keyframe or delta carries only the sections the attachment asked for, re-encoded with a shorter section table. And it compiles the floor: drawing needs each cell's centre, kind and size, which the world document states as entities and components that only the simulator's map compiler turns into a floor; rather than compile that in the browser, the server compiles the document once per run and includes the compact floor in the filtered scenario block. The browser still receives the world document itself, parsed in wasm by the world-protocol library, which is plain data and needs nothing of the simulator; that is what the entity inspector reads when it comes to the web UI. The recording itself is unchanged by either.

03 · the browser UI

A React shell around a WebGPU viewer compiled from Rust

The UI is the existing crucible-ui application: a React and TypeScript shell (Vite, uPlot for the charts) that owns the sidebar, the run list, the playback controls and the charts, and a canvas that belongs to the viewer. The viewer is Rust: studio/viewer, compiled to WebAssembly with wasm-bindgen and driving the canvas through wgpu's WebGPU backend, with WebGL as the fallback. The TypeScript wrapper studio/viewer/js loads the wasm module and exposes it to the shell.

The shell hands every binary message to the viewer unopened. The viewer decodes the frame with the worldview crate compiled to wasm, applies it to its state (a keyframe replaces, a delta advances), and draws the instant the shell's cursor points at, interpolating movers along their step lists inside a slice. Scrubbing within the frames the viewer holds costs nothing; scrubbing outside them makes the shell re-attach at the wanted instant, and the viewer rebuilds from the keyframe it is sent. The charts are the shell's: they show the series the server assembled from the recording's scalars sections.

What the browser needs from the wire is therefore small: the compiled floor, the playback section of one keyframe and of every delta after it, the scalars section for the charts, and the heat section when the heat overlay is on. The tables section never travels to a browser.

The entity explorer, desvis's roll of every entity in the world document with its components and the cells it derived, keeps working in desvis unchanged: it reads the loaded world document, which a recording now carries in its scenario block. Bringing it to the browser later needs three things the filtered scenario block can carry: the world document's own bytes, parsed in the browser by the world-protocol library; the id tables; and the census the server computes once per run (which cells each entity derived, which entity each cell is), because that census comes from the simulator's map compiler. The shared renderer draws the hover outline; the shell draws the roll. Nothing in it needs the simulator in the browser.

04 · rendering, shared

One renderer for desvis and the browser

Today there are two wgpu renderers of the same floor: desvis's, under desvis/src/gpu (about 3,900 lines: camera, grid pipeline, cell layer, bots, totes, arrows, rack frames, and the meshes its inspection panels use), and the prototype browser viewer's, under studio/viewer/src/gpu, with five shader files of the same names. Every fix to one has had to be made twice, and the two have already drifted. This phase makes one crate of the drawing code and has both viewers use it.

The crate is carved out of desvis, not written fresh. desvis's renderer is the more complete of the two and is the one the parity gate measures, so its drawing code moves: desvis/src/gpu/camera/ (math, projection, input) and desvis/src/gpu/renderer/ (the grid pipeline, the cell layer, instances, bots, totes, arrows, rack frames) and the five shaders become worldview/worldview-render, with their history preserved as a move. desvis keeps what is its own: the egui panels, tooltips and the picking and selection its inspectors run on, which call into the crate. The meshes go where the pipeline that draws them goes — the HTM body with the robot pipeline, the container shell with the container pipeline — so a robot and a tote look the same in both viewers. The prototype browser viewer's copy of the renderer is deleted, and the two things it did better than desvis, placing cells by their centres from a floor with no lattice and selecting the cell whose square holds the pointer, are folded into the crate before the copy goes. After the move, a change to how a bot or a tote is drawn is made once and both viewers get it.

The boundary of the shared crate is drawing: it renders a playback state at an instant into a wgpu surface. What is not shared stays with each viewer: desvis's egui panels, tooltips and inspection meshes; the browser's DOM, sidebar and charts. The first thing the shared crate's tests assert is that both viewers draw the same instance buffers for the same state, so a drift between the two viewers becomes a failing test rather than a screenshot comparison.

05 · development

dev.sh start gives a working UI

studio/runs/dev.sh start brings up PostgreSQL in a container on a port derived from the checkout, builds the server in the release profile (the simulator runs inside it, and the dev profile runs it at a third of real time), builds the wasm viewer, starts the server and the UI's dev server, and prints the UI's address. Submitting a run takes the UI's form or the terminal client. Nothing else is containerised, and no image builds are part of this phase. dev.sh status, logs, stop and stop --db do what they say. studio/runs/README.md has the commands and what each step costs on a developer's machine.

06 · what is not here

Watching a run as it executes, and the fleet

Watching a run while it executes is not in this branch. A run can be opened once its attempt has ended; until then the run list shows its state and its simulated clock counting up, and the shell attaches on its own as soon as a recording is stored. What live watching waits on is the simulator, not the server or the browser: the simulator's only present is the scheduler's trailing global barrier, so frames can be emitted only for the time buckets that barrier has already passed, out of an accumulator running ahead of it, and what is emitted is final. That needs one rule the simulator does not yet keep — no event may be emitted with a timestamp behind the barrier — and the work lives on its own branch, agent/worldview-emit. Nothing of it is built here: no live file, no provisional values, no second writer. When it lands, the server writes while a run executes and an attachment tails that file; the protocol, the format and the UI already say what to do with the frames, which is why attach takes "live" and the shell follows a run before it has a recording.

The prototype on agent/crucible-streaming split the server into brokers and a horizontally scaled deployment of runner processes, with a protocol between them, redispatch of a run whose runner died, container images for both and a workflow that built them. None of that is carried into this phase. The server runs simulations in-process, as studio/runs does today; the storage interface, the client protocol, the viewer and the development runner are the parts of the prototype that carry forward. When the fleet returns as its own initiative, the recording, the protocol and the UI are unchanged by it: a runner would produce the same frames into the same sink.

07 · done means

Open a run, scrub, seek, reload, and take the workbook

From a fresh clone: dev.sh start, open the UI, submit the cencora fixture, watch its progress count up, open it when it finishes with robots and totes moving on the floor and the charts filled, play, scrub inside the held window, seek outside it, reload the page and re-attach at an instant, turn each overlay and view on, open the DFW6 site, cancel a run and open what it recorded, submit a spec with its own files, and build a workbook from the stored recording. Both viewers draw the same instance buffers for the same recording, asserted by the shared crate's tests. The walk is driven headlessly by scripts/worldview/ui_gate.mjs, which asserts every step before photographing it.
