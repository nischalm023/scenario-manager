# Generating simulation reports

This guide describes a reusable workflow for simulation reports: defining
experiments, retaining recordings, extracting and validating measurements,
producing a single-page comparison and a per-variant breakdown, reviewing their
presentation, and packaging the results for colleagues.

The September 14 Walmart comparison is the worked example. Its case names,
warehouse parameters and results illustrate the process; they are not defaults
for other scenarios. The current matrix templates contain those specific
assumptions, and this guide identifies where to adapt them for future reports.

The two outputs serve different purposes:

| Output | Purpose | Source |
| --- | --- | --- |
| **Single-page report — `report.html`** | One scrolling document with findings, the comparison matrix, selected throughput curves, source-file analysis, spatial traffic figures, limitations and evidence links. “One page” means one HTML document, not one printed sheet. | [`report.py`](../scripts/walmart_matrix/report.py) |
| **Variant breakdown — `variants.html`** | One interactive HTML file with a view for each variant: throughput, putaway fills/stores, inventory, navigational waiting, exact configuration and downloadable data. | [`variants.py`](../scripts/walmart_matrix/variants.py), [`variants.js`](../scripts/walmart_matrix/variants.js), [`variants.css`](../scripts/walmart_matrix/variants.css) |

The measurements and figures are generated by the utilities. The interpretation,
comparison choices, caveats and suggested experiments are authored prose in the
templates. New data does not automatically make that prose correct.

See the finished [single-page report](easyloop/overnight-2026-09-14/report.html) and
[variant breakdown](easyloop/overnight-2026-09-14/variants.html), the
[tool reference](../scripts/walmart_matrix/README.md), and the
[`traffic_report` field/CLI reference](../native-modules/src/migration/traffic_report/README.md).
For a live review of the worked example, use the
[Walmart baseline checkout/run instructions](walmart-baselines.md).

## 1. Choose what needs to be repeated

| Desired change | Work required |
| --- | --- |
| Send the existing reports with working evidence links | Package the finished HTML and linked evidence; no export or simulation. |
| Change wording, colors, layout or displayed comparisons | Edit the relevant template and regenerate HTML from existing analysis. |
| Change chart interval or displayed time window | Use the viewer's existing controls, or change its renderer; retain the exported counts and durations. |
| Add measurements that already exist in the recordings | Extend the exporter/auditor, re-extract profiles and validate the new calculations. |
| Add information absent from the recordings | Add simulator instrumentation and run new experiments. An absent historical field is not a measured zero. |
| Change a workflow, fleet, map, arrival rule, initial inventory or scheduling policy | Freeze a new experiment and run the simulator. Do not relabel old recordings. |

The pipeline is:

```text
frozen binary + inputs + resolved per-case spec + invocation
                              |
                       headless desvis
                              |
              finalized .worldview + log + outcome
                              |
             source audit / flow audit / buffer audit
             report facts / traffic export / backlog analysis
                        /                 \
                  report.py          variants.py
                        |            + five-minute exports
                  report.html             |
                                     variants.html
                        \                 /
                      browser review + package_reports.py
                              |
                  portable HTML/evidence ZIP
```

## 2. Tools and prerequisites

Run the commands below from the repository root. Build the regular binaries:

```sh
cargo build -p desvis -p native-modules --release --bin desvis --bin traffic_report
```

`traffic_report` lives in
[`native-modules/src/migration/traffic_report.rs`](../native-modules/src/migration/traffic_report.rs)
and builds to `target/release/traffic_report`. It reads a finalized
`.worldview` recording and writes JSON. It does not start simulations or render HTML.

The HTML generators and packager need Python 3.11 or newer, using its standard
library. The Python profile auditors and matrix analyzer need **Python 3.14**
for `compression.zstd`, plus `msgpack`. One setup usable for all Python steps is:

```sh
python3.14 -m venv ../notes/report-tools/python
../notes/report-tools/python/bin/python -m pip install msgpack
REPORT_PYTHON="$PWD/../notes/report-tools/python/bin/python"
```

Record the Python, msgpack, Rust and exporter versions with a new experiment.
Preserve `Cargo.lock` and the simulator source revision. The optional headless
browser check also needs Node.js, Playwright and its Chromium installation;
setup appears in section 10. Viewing the final HTML requires only a browser.

## 3. Keep the experiment and its report revisions separate

The September 14 recordings live outside Git at
`../notes/walmart-matrix-2026-09-14`. A fresh clone contains the tools and
finished HTML, **not** the retained recordings and analysis directory. The
portable report ZIP contains evidence, but is not a full reproduction archive.

Use a separate directory for each new experiment and a new output folder for
each report revision. Retain the previous interpretation and its supporting
measurements when comparing revisions.

```text
experiment/
  manifest.json                     # Frozen controls, input hashes, cases
  source-audit.json                 # Stock/order counts and timing observations
  desvis-<iteration>                # Frozen release executable
  inputs/
    walmart_dfw6.json
    onhand.csv
    outbound.csv
    walmart_demo_stock_top_up.csv
  <case-id>/
    spec.json                       # Resolved configuration used by the run
    state.json                      # Outcome, timestamps, exit code, invocation
    run.log
    <recording>.worldview            # Exactly one recording per recorded case
    flow-audit.json
    buffer-audit.json
    traffic.json
    report-facts.json
    backlog.json
    variant-series.json             # Cached export, regenerated when needed
    *-audit.log / *-error.json       # Preserve failures as evidence

report-revision/
  report.html
  variants.html
  qa/
  reports.zip
```

The manifest records the frozen simulator binary and its SHA-256, source commit,
input hashes, seed, fleets, shared settings and the case list. Each case records
at least its `id`, `spec`, `spec_sha256`, `args`, `iteration`, `hours`,
`common_horizon_hours`, `preload_fraction`, `putaway`, `timing`, `sequence`,
`lead_time_secs` and `alias_of`. Preserve all fields when relocating an archive.

The current readers use these outcomes:

| `state.json` status | Meaning |
| --- | --- |
| `queued`, `running` | No completed result yet. |
| `finished` | The process returned successfully; its recording still needs auditing. A time-limited run need not finish every order. |
| `failed` | Inspect the log. A recognized stock-preflight rejection is distinct from a planner/runtime failure. |
| `equivalent_no_inbound` | A declared equivalent configuration with `alias_of`, not another measured run. |

A finalized recording may end earlier than its requested horizon. Preserve the
actual stop reason and duration. A successful audit establishes consistency of
recorded behavior; it does not establish the fidelity of every warehouse rule.

If the archive moves, preserve file contents and resolve the spec's world/CSV
paths against the relocated inputs. Also update manifest invocation/spec paths
and analysis provenance paths when those are used by a command. Record any
path-only spec rewrite and its new hash. `package_reports.py` can relocate the
linked evidence independently because it resolves `<case-id>/<file>` under
`--base`. It does not rewrite simulation configurations inside JSON evidence.

## 4. Define the comparison before launching it

Write a hypothesis, identify the variable being changed, and list the controls.
Keep map, seed, inventory distribution, fleet, operator times, extraction,
buffer behavior, order population and observation windows fixed unless they
are deliberate dimensions of the experiment.

The September 14 matrix varied:

| Dimension | Values |
| --- | --- |
| Initial stock | Full, partial, empty |
| Putaway | Disabled or enabled |
| Order eligibility | Source `order_drop_time` or all orders released at T0 |
| Synthetic induction sequence | `order_release` or `sku_demand` |
| Induction availability sensitivity | All lots available at T0, or one hour before their source-order release |

It contained 18 configurations: 12 recordings, four expected stock-preflight
rejections and two explicitly equivalent configurations. Most horizons were
16 hours; two source-timed cases requested 52 hours. Comparisons use a common
first-16-hour window as well as each recording's whole observed duration.

The frozen controls were 230 HTMs, 48 VTMs, 128 reusable trays, four EasyLoops,
10 seconds per operator transfer, queue factor 3, physical box induction and
extraction, and a synthetic one-hour DS buffer hold. The 128-tray setting is a
diagnostic override; it differs from the 24-tray repository presets. The VTM
total is 40 inventory plus eight buffer/storage VTMs, pending site confirmation.

Putaway used six stations, each targeting 60 fills/hour, with up to six units
of one SKU per synthetic fill. This was a provisional model, not a supplied
receiving schedule. Inventory in general supports mixed-SKU totes; the current
synthetic fill policy is more restrictive.

Keep collision avoidance at its normal setting. Keep all source orders in the
real scenario; use a clearly labelled order cap or shorter horizon only for
development validation. Release all orders at T0 for saturated-throughput
comparisons, and separately test source timing for the actual workload shape.

Do not attribute a full-versus-partial preload difference solely to putaway.
Initial SKU availability and placement change too. Additional seeds and longer
windows are needed to assess variability and persistent behavior.

## 5. Audit the stock and order files first

Create the resolved specs and frozen input copies, then run:

```sh
REPORT_ARTIFACTS="/absolute/path/to/experiment"
REPORT_OUTPUT="/absolute/path/to/report-revision"
"$REPORT_PYTHON" scripts/walmart_matrix/analyze.py \
  --base "$REPORT_ARTIFACTS" --sources
```

This writes `source-audit.json`. Inspect the actual column names, SKU coverage,
quantities, top-ups, order counts, line counts, release distribution and
inconsistent timestamps. The source auditor currently expects the Walmart
CSV schemas and filenames shown above; adapt it for another source format.

The September 14 source facts are useful cross-checks when reproducing that
exact archive:

| Fact | Value / interpretation |
| --- | --- |
| On-hand snapshot | 174,997 SKUs; 1,397,589 units |
| Approved demo top-up | 43 additional units across 40 SKUs |
| Full preload | 1,397,632 units in 162,060 stocked inventory totes |
| Partial preload | 747,243 units in 81,030 stocked inventory totes |
| Empty preload | Zero stocked units; empty inventory totes still exist in racks |
| Orders | 22,160 orders, 24,789 lines, 25,625 requested units |
| Release span | About 47.28 hours; only 245 orders in the first six hours |

Partial preload applies 50% **per SKU, rounded upward**, so its total is 53.46%
of full stock. Initial inventory plus the remaining finite inbound workload
must conserve the approved stock total. Putaway must not duplicate preload.
“Full” means all approved stock, not full rack occupancy or 100 units per tote.

The on-hand file has no receiving/induction timestamps or physical tote-content
assignments. Order release timestamps lack a timezone offset. `cutoff_time`
has time-of-day values whose operational meaning remains unconfirmed. Do not
infer a receiving schedule or truck-release rule from those fields.

For cold-start experiments, distinguish induction **sequence**, lot
**availability**, physical fill time and rack-store completion. Static
`order_release` sequencing can still differ from live assignment once released
orders accumulate, because assignment can fall back to order-ID priority.
Low picking with empty initial stock is not by itself evidence of congestion.

## 6. Collect new recordings only when needed

[`run.py`](../scripts/walmart_matrix/run.py) is the dated September 14
supervisor. `--prepare` freezes its matrix; it refuses an existing manifest.
`--supervise` starts queued cases. It is **not** a generic scenario/matrix CLI:
for a new experiment, revise its `BASE`, template, case definitions, labels,
input list and manifest assumptions first. Do not point an unreviewed runner
at the completed archive.

The original preparation/execution sequence was:

```sh
"$REPORT_PYTHON" scripts/walmart_matrix/run.py --prepare
"$REPORT_PYTHON" scripts/walmart_matrix/run.py --supervise
```

For an individually prepared case, the equivalent recording command is:

```sh
/absolute/path/to/frozen/desvis /absolute/path/to/case/spec.json \
  --headless --progress --simtime 16h --wall-timeout 3h \
  --allow-incomplete --output-dir /absolute/path/to/case \
  --name partial-on-t0-order_release \
  --label "Walmart iteration NN | partial preload | putaway on | T0 | 16h"
```

Use a unique output directory for each execution. The supervisor records the
exact arguments, process outcome, log, timestamps and sampled memory usage.
Manual executions need equivalent records and a matching manifest entry before
the matrix tools can consume them.

`--allow-incomplete` permits a bounded experiment to stop with orders remaining;
it is not permission to ignore a failed preflight or inconsistent recording.
The CLI's simulation horizon accepts `16h`; the Rust exporter's positional
horizon is a numeric number of hours, such as `16`.

The existing supervisor permits at most four headless runs and requires
available-memory headroom before adding a run. Its memory probe is macOS
specific. Keep at most two headed desvis instances open. Monitor actual RSS,
memory pressure and run health; do not size concurrency from CPU cores alone.

For human inspection, launch `desvis spec.json --run --simtime 16h --label ...`.
The GUI stays open after calculation. Omit `--run` when inspecting the map before
starting. Use headless mode for the recorded batch workflow: its `--output-dir`
and `--name` flags control profile output. A headed review is not automatically
a retained batch recording.

## 7. Extract and validate measurements

For one finalized recording, independent of the matrix templates:

```sh
target/release/traffic_report \
  /absolute/path/to/case/run.worldview \
  /absolute/path/to/case/spec.json \
  16 /absolute/path/to/measurements.json --series-minutes 5
```

Use the matching world/spec: cell IDs, equipment membership and inventory-zone
roles determine how the movement records are interpreted. The output parent
must exist. This reader streams playback slices, but series extraction also
retains relevant journals, rack snapshots and per-bin aggregates. A short
measurement cutoff still requires reading through the compressed recording.

For a complete matrix case:

```sh
"$REPORT_PYTHON" scripts/walmart_matrix/analyze.py \
  --base "$REPORT_ARTIFACTS" partial-on-t0-order_release
```

This replaces that case's analysis files. It runs:

| Analysis | Output and purpose |
| --- | --- |
| [`audit_flow_profile.py`](../scripts/audit_flow_profile.py) | `flow-audit.json`: completion counts, inventory balance, motion and event coverage |
| [`audit_buffer_profile.py`](../scripts/audit_buffer_profile.py) | `buffer-audit.json`: independent buffer timelines, rack occupancy and residence accounting |
| `traffic_report` | `traffic.json`: cumulative cell traffic through the common 16-hour horizon |
| `analyze.py` journal scan | `report-facts.json`: common/whole-window throughput, peaks, fleet duty and station populations |
| [`backlog.py`](../scripts/walmart_matrix/backlog.py) | `backlog.json`: recorded order phases versus available stock; requires the frozen Walmart CSVs |

The current analyzer uses Walmart buffer zones **21–28**, four stations and a
16-hour common horizon. Those are analysis assumptions to update for another
map or experiment. `--refresh-completed` is a historical flow-cutoff repair
operation; it is not a general refresh of every analysis. Use the case command
when all derived facts for a case need rebuilding.

To audit newly finished cases while a prepared matrix runs, or to fill missing
analysis for an already finished matrix:

```sh
"$REPORT_PYTHON" scripts/walmart_matrix/analyze.py \
  --base "$REPORT_ARTIFACTS" \
  --report-output "$REPORT_OUTPUT/report.html" --watch
```

The watcher does not launch simulations. It skips cases with existing report
facts or recorded analysis errors; it is not a forced re-audit. It refreshes
the single-page HTML, so give it a new output location. Use one analyzer per
artifact directory; the watcher takes a directory lock.

Check the **results**, not just whether a command finished. Preserve
`audit_exit_codes`, audit `errors`, analysis/backlog error files and failing
logs. Some batch operations intentionally retain failed evidence and continue.
Required reconciliations include:

- Count completions at physical completion time through the observation cutoff.
  Future accepted work is not completed throughput.
- Initial inventory + inducted units − picked units = remaining inventory.
  Count inventory in circulation as well as stored stock where the ledger does.
- Separate inducted units, filled totes and completed filled-tote rack stores.
  Returning inventory from picking or moving order containers is not putaway.
- Buffer occupancy from physical container timelines must agree with physical
  rack state, including containers still stored at the cutoff.
- Canonical HTM movement must cover playback, with no overlaps or unexplained
  duration difference. Rotation and stationary waiting are separate populations.
- Sum five-minute flow counts against independent journals; sum eligible wait
  durations against cumulative traffic; reconcile rack occupancy identities.

Expected negative cases stay visible as preflight rejections with no invented
charts or zero-rate claims. Equivalent cases identify their source recording
and clip it to the equivalent case's requested horizon.

## 8. Generate both HTML documents

With completed analysis available, these commands do not run the simulator:

```sh
"$REPORT_PYTHON" scripts/walmart_matrix/report.py \
  --base "$REPORT_ARTIFACTS" --output "$REPORT_OUTPUT/report.html"

"$REPORT_PYTHON" scripts/walmart_matrix/variants.py \
  --base "$REPORT_ARTIFACTS" \
  --original-report "$REPORT_OUTPUT/report.html" \
  --output "$REPORT_OUTPUT/variants.html"
```

Keep the filenames `report.html` and `variants.html` together: the viewer links
to `report.html`. Explicit output options protect earlier report revisions.
The defaults still target the checked-in September 14 documents.

The first command assembles existing facts, figures and authored interpretation.
The second invokes `traffic_report --series-minutes 5` as needed. Its
`variant-series.json` caches are keyed by the profile, spec and exporter hashes
and the five-minute bin width. `--extractor` selects a frozen exporter binary;
`--refresh` forces re-extraction. A rebuilt exporter can invalidate caches even
when its measurement logic is unchanged.

The variant generator embeds the dataset, CSS and chart JavaScript. It records
the chosen single-page report's hash and checks that generating the companion
did not change that file. The viewer offers 15-minute/hourly bins, whole/common
windows, shared/local scales, hover/keyboard values, CSV rows and a JSON download
of the complete embedded dataset. Those downloads require no separate JSON file.

## 9. Preserve the measurement definitions

| Measure | Definition |
| --- | --- |
| Pick rate | Completed picked **units** divided by observed simulated hours |
| Operator transfer rate | Completed transfer tasks divided by observed hours; can differ from unit rate |
| Inducted units/hour | Units added at completed decant fills divided by observed hours |
| Filled totes/hour | Completed decant fills divided by observed hours |
| Putaway totes stored/hour | Completed return VTM stores for filled putaway totes divided by observed hours |
| Navigational wait | Sum of eligible HTM stationary time, normalized as minutes per configured HTM per simulated hour |
| Inventory units | Initial preload + completed induction − completed picking; not just rack-resident units |
| Rack fill | Physical source-inventory slots at a timestamp, distinguishing stocked, empty-tote and unknown occupancy |

For an interval of duration `hours` with `fleet` HTMs:

```text
pick_units_per_hour = picked_units / hours
wait_minutes_per_htm_per_hour = eligible_wait_ms / 60_000 / fleet / hours
```

Rebin by summing counts and exposure before dividing. Do not average rates from
unequal-duration intervals. Clip at the earlier of requested cutoff and recorded
end. A partial final interval uses its actual duration and is labelled; exclude
it from **peak complete-hour** comparisons. A rolling-hour peak is a different
statistic from a peak fixed hour. Ordinary flow bins are `[start, end)`; a
completion exactly at the final observation cutoff belongs in the final bin.

The current model's four operators × 3,600 / 10 gives **1,440 transfers/hour**.
Do not present that as a universal unit-rate ceiling when transfers can contain
multiple units. Separate startup, saturated operation and workload drain.

The shared navigational-wait filter is
[`WarehouseMap::navigation_wait_exclusions`](../sim/desmap/src/map/navigation_wait.rs).
Both the exporter and desvis heatmap use it. It excludes typed queue,
presentation, exchange, relay and charging cells; relay access; station and
handoff queues; inventory holding queues; and complete conveyor-equipment
membership, including EasyLoop waiting blocks and circulation cells. It also
catches operational waiting cells whose traversal type is `Open`. An ordinary
upstream travel cell remains included. Change this common filter, not separate
ad hoc lists in each chart.

Eligible waiting is a **location-based** measure, not a causal congestion
counter. Idle/resource/task holds can remain in ordinary travel cells.
`implicit_hold_ms` is a subset of total stationary waiting; do not add it again.
The denominator includes the configured HTM fleet, including idle robots.

Speed comes from canonical kinematics, using duration-weighted half-metre/second
bins and cell attribution across links. Its mean excludes stops and in-place
rotation. A median inferred from those bins is approximate. Show exposure and
the distribution as well as the mean: a mixture of slow and fast movement does
not establish that crossing traffic interrupted a fast traffic wave. That
requires direction/time analysis around the affected cells.

For the September 14 map, source-inventory rack capacity is **170,570 slots**.
The old loader diagnostic's 174,020 includes 3,450 order-storage slots. Use the
inventory-zone denominator from the export. `occupied = stocked + empty +
unknown`; an empty inventory start can still have high empty-tote occupancy.
Exporter `net_inventory_units` excludes preload, so the renderer adds the
independently established initial inventory exactly once.

When using Little's law, match the stage and population: logical inventory
credits, loaded HTMs awaiting boarding, conveyor totes and resident order HTMs
have different lifetimes. Use observed stage WIP, stage completions and stage
residence times over compatible windows. Do not substitute an upstream CONWIP
limit for measured physical congestion or assume a queue factor guarantees
operator saturation.

## 10. Review the rendered result

Automated validation complements a visual and editorial review. For optional
isolated browser checks, install the tools outside the source tree:

```sh
npm install --prefix ../notes/report-tools/browser playwright
../notes/report-tools/browser/node_modules/.bin/playwright install chromium
NODE_PATH="$PWD/../notes/report-tools/browser/node_modules" \
  node scripts/walmart_matrix/check_html.cjs "$REPORT_OUTPUT" "$REPORT_OUTPUT/qa"
```

[`check_html.cjs`](../scripts/walmart_matrix/check_html.cjs) opens both HTML
files in a headless, offline browser. It checks matrix/variant counts, charts,
displayed mean rates, interval/window/scale controls, keyboard values,
CSV/embedded-JSON downloads, the report link and desktop/mobile overflow. It
writes screenshots and `html-validation.json`. It does not attach to anyone's
Chrome session or foreground applications.

Inspect the screenshots and the actual report. Verify readable axes/legends,
units, scale choices, partial bins, the long source-timed recording, at least
one rejected and one equivalent case, and a mixed pick/putaway case. Review
every interpretive paragraph against the current measurements. The checker
cannot establish that a narrative claim is true or a warehouse model is valid.

For exporter changes, the focused tests are:

```sh
cargo test -p native-modules --release --bin traffic_report
```

Also compare a retained recording against an independent audit and the prior
export. Tests of bin splitting alone cannot establish correct full-run totals.
Do not rerun the simulation solely to verify a rendering change.

## 11. Package and share

```sh
"$REPORT_PYTHON" scripts/walmart_matrix/package_reports.py \
  --base "$REPORT_ARTIFACTS" --documents "$REPORT_OUTPUT" \
  --output "$REPORT_OUTPUT/reports.zip"
```

The ZIP contains both HTML documents, referenced JSON/log evidence, a short
README and a manifest of source/packaged hashes. For the September 14 pair that
is 72 JSON evidence files and four preflight logs, in addition to the reports
and package metadata. The packager rewrites links only in the packaged copies,
checks static links/anchors, parses included JSON and checks archive integrity.
It also labels the companion's original-report hash as the **source** hash,
because the packaged report's relative-link rewrite changes its bytes.

Unzip into a different folder and repeat the browser check there. Open a JSON
evidence link and a preflight log as well as exercising downloads. A two-HTML
ZIP displays the embedded figures but leaves the original report's absolute
evidence links broken for colleagues.

Sharing instructions: **unzip the entire archive, keep its folders together,
and open `variants.html`**. The figures and downloads work offline. No simulator,
web server or Rust/Python installation is needed to read the reports. Sending
through Slack is a separate user action; producing the bundle does not send it.

Keep the full experiment archive separately for re-analysis: recordings,
matching inputs/specs, binary, manifest, raw logs and analysis tools/revisions.
The report ZIP intentionally excludes large recordings, binaries and source
fixtures. Commit the utilities, guide and reviewed HTML revisions; retain large
run artifacts outside Git with a documented storage location.

## 12. Adapt and refine the report deliberately

The input/output options make report revisions repeatable, but these are still
**Walmart experiment templates**, not an arbitrary warehouse-report framework.

| Change | Places to review |
| --- | --- |
| New experiment or source files | `run.py` matrix/manifest/input copies; `analyze.py::source_audit`; `backlog.py` CSV identity/order mapping |
| New case IDs, cases or preload values | Named comparisons and prose in `report.py`; labels/default selection/narrative in `variants.js`; header/date/counts in `variants.py` |
| Different fleets, equipment or buffer zones | Manifest/specs; analyzer station loops and buffer zones; denominators and explanatory prose in both templates |
| Different common horizon or sample width | Analyzer's 16-hour window/traffic cutoff; exporter interval; viewer's common cutoff/rebin logic; labels and peak definitions |
| New metric | Simulator instrumentation if absent; generic exporter/auditor; independent reconciliation; HTML series/units/tooltips/downloads |
| Different navigation-wait membership | Shared map filter and its tests; re-extract traffic and series; disclose the definition change |
| Visual changes | `variants.css` / `variants.js`; single-page CSS/SVG helpers in `report.py`; background browser checks and visual review |
| Interpretation | Findings, case notes, selected comparisons, controls, questions and recommended experiments in both templates |

In particular, the templates contain authored September 14 conclusions, case
IDs, date labels, the 18-case summary, a 230-HTM explanation, a 16-hour common
window and site-specific numbers. Merely swapping the manifest cannot make
those statements applicable to a different experiment. Rewrite them or move
them into explicit report metadata as the next generalization step.

Keep new experiments small enough to explain causally. Useful refinements here
include stock-ready order assignment, induction that responds to assigned
shortages, calibrated inbound tote contents/timing, and direction/time traffic
analysis around apron hotspots. State each as a hypothesis with measurements
that could disprove it. Reassess floor-driving VTMs, charging, buffer release
and downstream box handling before treating simulated throughput as a validated
site-capacity result.

## Troubleshooting

| Symptom | Check |
| --- | --- |
| `compression` cannot be imported | Use Python 3.14 for profile analysis. |
| `msgpack` cannot be imported | Install it in the same Python environment used by the analyzer. |
| Missing profile, or multiple profiles for a case | Keep exactly one finalized recording per case/execution directory. |
| Export fails on finalization/motion coverage | The recording is incomplete or lacks required canonical motion; do not manufacture measurements. |
| Unexpected re-extraction | Profile, spec or exporter hash changed; inspect the cache signature. |
| Mean/peak numbers disagree | Compare the same units, observed cutoff, bin width, partial-bin policy and fixed-versus-rolling peak. |
| Inventory fill disagrees | Separate stock units, stocked totes, all occupied totes and source-only rack capacity. |
| Empty start picks very little | Check stock readiness and induction/assignment priority before blaming traffic. |
| Figure is absent | Distinguish unavailable data, rejected preflight, pending analysis and an observed zero. |
| Evidence links fail after sharing | Use the packager and extract its entire directory tree. |
| Relocated archive fails to load | Resolve world/input/spec/provenance paths against the preserved files and check hashes. |
| New results appear under old claims | Review hard-coded dates, case names, controls and authored interpretation in both templates. |
