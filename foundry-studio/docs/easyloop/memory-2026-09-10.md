# Simulation memory, September 10

Iteration 08 (`desvis-supply-overlap`, `f08e1e14a`) reached a 91.5 GiB
physical footprint after about five and a half wall-clock hours. The macOS
allocator reported 38.5 GiB of allocated objects and 51.5 GiB of fragmentation
and unused allocator space. These are one process sample, not a leak census.

The recording implementation copied every tote location into every time slice,
even when the tote never moved. Live publication repeatedly reconstructed that
history and queued complete revisions on an unbounded channel. The UI then
cloned the received payload again. A three-second stack sample found 1,206 of
2,103 observer-thread samples in `finalize_tote_states` and another 584 in the
call to `flush_dirty`. The planner was also active; this was not evidence of an
idle scheduler spinning through empty timestamps.

## First correction

- Keep the initial tote-location checkpoint once; subsequent slices contain
  timed changes. Tote creation, contents and conveyor transit records retain
  their physical timestamps. Reverse scrubbing and earlier corrections rebuild
  from the relevant checkpoint.
- Coalesce unpublished cumulative revisions by slice start time. A stalled
  viewer retains at most one pending revision per distinct slice; it cannot
  accumulate repeated copies of the same interval. This is not a fixed total
  memory limit: the distinct history can still grow.
- Move drained payloads into the UI's retained records. Preserve every distinct
  interval, including corrections to earlier intervals.
- Teach both Desvis and Crucible to reconstruct sparse locations. New profiles
  use container revision 4 so older viewers refuse them rather than silently
  showing empty tote states. Existing revision-3 checkpoint profiles remain
  readable; retired revisions 1 and 2 remain rejected.

The full-warehouse regression uses 162,060 stationary totes, ten-second slices
and six simulated hours. The tote-location arrays contain 1,944,720 bytes,
versus 4,202,539,920 bytes for the previous repeated snapshots. This measures
one component of one retained copy, not total process memory or all of the
91.5 GiB observed in iteration 08.

## Shared inventory index

An initialization check with the same full inventory and orders already peaks
at 13.27 GiB. Inspection found that the relay inventory index repeats SKU/tote
membership for every relay serving a rack, typically 56 times. A live allocator
sample contains roughly 38.9 million small allocations.

SKU/tote membership now lives once per aisle side. Each member retains its rack
slot and last accepted write time. Queries calculate each relay's travel cost
from that slot and retain the original cost/ToteId tie-break. Removal timestamps
still prevent an older event from resurrecting an unavailable tote. Order-tote,
empty-tote and empty-slot indexes retain their existing representation.

The same initialization check now peaks at **3.24 GiB**, down **75.6%**. The
measured startup includes initial task admission and planning, with zero picks;
it is not a loader-only allocation census. This is a direct comparison between
the two headless builds, with the same full map, inventory and source orders.

The frozen binary is `desvis-shared-inventory-index`; its input and source hashes
are recorded in `shared-inventory-index-manifest.json` beside the run evidence.
This index changes when costs are calculated, so query CPU remains a tradeoff
to measure, particularly for SKUs with many eligible totes.

All 29 relay-index tests pass. An independent reference keeps the old per-relay
cost frontiers and compares candidates through reservations, returns, mixed-SKU
contents changes and late writes. Additional coverage checks cross-side moves,
unreachable zones, skip-zone filtering and membership storage with 1 versus 56
same-side relays. Release compilation, qualified-path and whitespace checks pass.

The matching seven-hour run peaks at **4.38 GiB**, versus **14.01 GiB** after the
playback correction alone: **68.7% lower peak RSS**. Both runs finish 685 orders
and 768 picks with 939,754 events. Canonical hashes match for all 2,522 intervals
of robot movement, relay state, tote state and station diagnostics. Collision
avoidance remains enabled and source arrival timestamps are unchanged.

Wall time increases from 253.2 to 269.4 seconds (6.4%) in this single comparison;
user CPU increases from 258.5 to 277.4 seconds. Background workloads were not
isolated, so this does not establish the precise query-cost penalty. No CPU
speedup is claimed. The remaining live headed window still runs the previous
binary; the full 47-hour arrival span and headed memory plateau have not been
validated with these corrections.

## Follow-on design choices

For colleagues reviewing the recording design, agree on these boundaries:

1. Initial state plus ordered changes, with occasional checkpoints when seeking
   cost justifies them. Do not repeat the whole warehouse at a fixed short cadence.
2. Separate live display delivery from durable history. Superseded cumulative
   display revisions may be discarded; physical events may not.
3. Incremental metric reconstruction with explicit handling of earlier events.
   Physical inventory currently rebuilds its complete history on live refresh,
   and remains a candidate for CPU and allocation reduction.
4. A memory budget and disk-backed older history for long runs. The current
   correction does not add disk paging, incremental physical metrics, or a
   bounded event-capture channel.
5. Shared inventory membership, with relay-specific costs calculated separately.
   Reachability should not multiply copies of the same inventory facts.

The first throughput benchmarks intentionally used an available-at-start order
backlog. Iteration 08 respects `order_drop_time`; only 245 orders arrive in its
first six hours. All 22,160 source orders have consistent drop timestamps across
their lines. We interpret this field as an order release gate, analogous in that
respect to NET; the business definition still needs site confirmation.
