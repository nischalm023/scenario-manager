# EasyLoop fulfillment architecture review

## Findings against the current hypotheses

The current code already models a real item-transfer task and an exclusive operator. `FulfillOrder` creates `TransferItems` only after the inventory tote is presented and the order HTM has physically navigated to the chosen order presentation cell (`orders.rs:598-669`). `TransferItems` asks the conveyance for a paired interval, mutates both tote ledgers at its end, records the pick, and emits processing/waiting state (`transfer_items.rs:153-231`). This is not merely a fixed robot dwell.

Operator exclusion is explicit and is shared across both APP sides of one conveyor machine. Every `Conveyance` has one `operator: Calendar` (`model/conveyance/mod.rs:71-81`); `try_pair` selects the first free operator interval and books it from `start` to `end` (`model/conveyance/mod.rs:321-358`). There is one `Conveyance` per conveyor-group/EasyLoop (`model/conveyance/machines.rs:26-44`), so the model has one exclusive operator per loop, not one per presentation side. This directly falsifies the suspected missing-operator defect.

Both physical presentations remain occupied through operator completion. `TransferItems::validate_transfer` requires the order cell reservation and robot plan to cover the entire paired interval, and requires inventory conveyor custody throughout it (`transfer_items.rs:80-129`). Committing the transfer advances the inventory presentation's `pick_end` to the paired end (`model/conveyance/claims.rs:155-172`); the caller clears it only at `pair.end`, with outbound conveyor travel afterward (`orders.rs:653-692`). The order HTM's committed station-work leg also ends at `pair.end` (`transfer_items.rs:171-184`). This behavior is correct for the stated APP semantics.

The current Walmart value is **9 seconds**, not 10. The Dallas template defaults `time_per_pick_secs` to 9 (`world-protocol/examples/walmart-dallas/catalog.json:107-126`), and `FulfillOrders` uses that value unless its task config supplies `pick_secs` (`orders.rs:151-160`). The retained iteration-10 log confirms the effective 9-second input and 144 HTMs / 48 VTMs (`/Users/daniel/vt/greyorange/notes/walmart-next-wave-2026-09-10/headed-iteration-10.log:3-26`) and records **5,397 completed pick tasks/presentations in eight hours**, or **674.625/site-hour, 168.656/loop-hour, and 84.328/APP-hour** (`/Users/daniel/vt/greyorange/notes/walmart-next-wave-2026-09-10/headed-iteration-10.log:138-152`). At nine seconds those intervals consume 42.16% of the four operators' combined eight-hour capacity. Changing to 10 seconds increases service demand per task by 11.11% and lowers the per-loop task ceiling from 400 to **360/hour**; four loops provide a loose aggregate ceiling of **1,440 transfer tasks/hour**. Comparing iteration 10's observed 9-second rate with that new ceiling is illustrative only. `TransferItems` can move `qty > 1` in one dwell (`transfer_items.rs:46-77`, `transfer_items.rs:185-202`), so whether the confirmed 10 seconds applies per unit or per tote/SKU transfer task remains a calibration question. Report units, transfer tasks/presentations, and completed orders separately.

Order assignment is currently conflated with a physical waiting-cell worker. Startup creates at most one `FulfillOrdersAtWaitingCell` per waiting cell, further capped by half the HTM fleet and the optional per-machine limit (`orders.rs:191-240`). Each worker claims exactly one next order, runs that order through all picks, and cannot claim another until the previous order's last waiting-berth hold has acquired a finite departure (`orders.rs:291-325`, `orders.rs:727-757`). A claim removes the order from the shared pending list (`pending_orders.rs:51-68`), but the order is not registered with the completion tracker until its entire SKU demand can be reserved (`orders.rs:451-485`). There is therefore no authoritative, observable state called “assigned to EasyLoop.” Depending on which internal milestone is counted, saturation can appear to be six, below six, or not yet admitted.

The current code prepares one inventory visit ahead, not one next order ahead. It starts the first supply concurrently with order-container acquisition (`orders.rs:488-540`), then after each pick starts only the next required SKU supply while the same order HTM returns to its berth (`orders.rs:693-704`). It does not prepare a successor order for that berth before the current one physically departs. This is a real missing capability relative to Daniel's saturation requirement.

Inventory sequencing is **not physical FIFO**. Presentation intents are sorted by `(inventory_ready, load identity, intent identity)`, not by conveyor boarding position (`model/conveyance/intents.rs:138-142`). An earlier-ready intent with a feasible APP approach is assigned first, which prevents a later-ready intent from taking that same side; the focused test verifies this behavior (`model/conveyance/intent_tests.rs:27-50`). But if the head intent has no feasible approach, `selected_quote` simply finds no `best` for it and continues to later intents (`model/conveyance/intents.rs:149-177`), allowing a later load to present. Within one intent it also chooses whichever APP produces the minimum predicted max of source and target arrivals (`model/conveyance/intents.rs:149-168`). There are no belt positions, predecessor links, overtaking constraints, or ring sequence. The model enforces readiness-ranked side allocation, not conveyor FIFO; this is a known fidelity gap against the newly stated non-resequenceable inventory rule.

Order HTMs are resequenced only indirectly. Each berth owns its current order; competing presentation intents can choose sides and are ranked by source readiness, while route availability changes can poison and recompute the choice (`present_tote.rs:185-310`). There is no station-level optimizer that compares all assigned orders and inventory sources as explicit pairs. The preferred side simply alternates for successive visits of an individual order (`orders.rs:557-565`). That leaves source/order matching quality as an inferred bottleneck. It is not a known correctness defect because both physical arrivals and all holds are validated before transfer.

Direct extraction is represented per order by `ExitPath`. `DispatchOrder` enters the buffer store/dwell/retrieve chain only for `ExitPath::Buffer`; all other orders navigate directly to a reachable extraction port (`orders.rs:801-870`). The current task config exposes pick, extraction, buffer dwell, and active-order limit, but no run-wide “force direct extraction” switch (`orders.rs:169-183`). A temporary isolation mode should be an explicit fulfillment policy override at composition/run config, applied before dispatch, rather than rewriting source orders or deleting buffer infrastructure. Keep the original requested exit path in telemetry so the experimental override remains auditable.

Direct extraction also changes the relevant downstream ceiling. With the current independent **three ports at 9 seconds**, the dwell-only ceiling is **1,200 orders/hour**. At the documented full-file average of **1.15636 units/order**, that is **1,387.63 units/hour** if demand mix and completions remain proportional (`docs/easyloop/review-verification-2026-09-08.md:169-176`). The requested **10-second EasyLoop operator** ceiling is 1,440 transfer tasks/presentations per hour across four loops. Those rates count different things: one order can require one or more transfer tasks, and one `TransferItems` task can move multiple units in one dwell. Whether the new 10 seconds is per unit or per tote/SKU transfer task remains a calibration question; units, transfer tasks/presentations, and orders must not be equated. If extraction dwell is also changed to 10 seconds—currently it defaults from the same operator input unless `extraction_secs` overrides it (`orders.rs:157-160`)—the extraction ceiling becomes **1,080 orders/hour**, equivalent to **1,248.87 units/hour** at that average mix. The direct-only experiment therefore needs separate pick and extraction dwell inputs and must report all three counts.

## Recommended decomposition

Keep the existing task boundaries and `Conveyance`; add one small **station coordination service** plus an explicit admission ledger. The coordinator owns logical states such as `Pending -> Assigned(station) -> Prepared -> Admitted(berth) -> Picking -> Outbound`, publishes their transitions, and chooses the next source/order/APP candidate. It should call the existing container acquisition, `SupplyConveyor`, `PrepareOrderPresentation`, `Navigate`, `TransferItems`, and `DispatchOrder` tasks rather than absorb their routing, custody, and inventory behavior. `Conveyance` remains authoritative for the eight inventory-tote capacity, APP claims, and exclusive operator. This avoids both the current one-worker-per-berth conflation and a new fulfillment god object.

The admission ledger separately records logical assignment/preparation limits and every physical commitment made for an order: berth, order HTM, APP approach/path, and outbound continuation. Assignment need not be physically empty, but each resource claim must be explicit and independently bounded. A practical control surface is:

- assigned-order target `A`, initially 6 and testable above 6;
- prepared-order target `P <= A`, counting orders with stock/container/source work in flight;
- station-footprint target `F`, counting all order HTMs committed to the station subsystem, including waiting berths, APP approaches/presentations, and any post-pick return-to-berth movement;
- conveyor inventory capacity 8, already enforced by `Conveyance`;
- APP and operator capacities, already enforced by `Conveyance`.

Daniel's proposed early dispatch should be tested, not ruled out. An assigned/prepared order above `W=6` may dispatch its HTM early when its next navigation task can reserve a **timed continuous route directly into a berth that is predicted to clear**. It must not stop in an undeclared floor cell, create a parking queue, or recursively reserve the order's full future task chain. The route claim is revocable until accepted through ordinary proposal competition. `F` is only an occupancy bound, not a deadlock proof: unfinished orders retain their return-berth claims, and admission must preserve feasible egress for APP occupants and returning orders already in flight. Candidate experiments should compare `A=6,7,8` and small `F` increments, measuring whether earlier dispatch hides berth-release latency without increasing blocked approaches or egress holds.

Pairing should reuse `PresentationIntent` but change its ordering contract to the physically confirmed conveyor order. The head inventory load may choose between feasible APPs based on order ETA; a later load cannot pass it merely because the head's matching order or side is unavailable. If real equipment permits a defined bypass, model that rule explicitly rather than deriving it from readiness. `TransferItems` remains the physical commit point and the current operator calendar remains unchanged.

## Deadlock and egress rules

Admission must be conservative about exits. Before accepting an early-dispatch plan, the coordinator must prove a time-bounded route to a declared berth, preserve enough station-footprint headroom for currently presenting orders to return or leave, and avoid consuming the final reachable egress needed by an APP occupant. Structural reachability alone is insufficient because open-ended holds can make a nominal route unusable. At scheduling time, avoid holding a destination APP while waiting for an unknown successor; retain the present rule that the task owning known next work owns departure planning. The current direct carton validation already requires a reachable parking/relay egress from extraction (`orders.rs:113-137`), and direct dispatch publishes departure requests so productive reuse can beat fallback parking (`orders.rs:829-905`). Preserve those safeguards.

For station internals, use acquire/commit ordering: create revocable source/order/side intentions first; atomically accept a pair; reserve the order route; commit the physical presentation and operator interval only when both claims remain valid. Never hold the operator while waiting for either arrival. Never release a berth, APP, conveyor slot, or extraction cell on a logical state transition; release it only when the corresponding physical reservation obtains a finite end. Keep the eight-tote conveyor capacity independent of the number of waiting cells, as it is today (`model/conveyance/machines.rs:14-15`, `model/conveyance/machines.rs:93-103`).

## Metrics needed before tuning

Add station-scoped interval events or snapshots for:

- assigned orders, prepared orders, admitted orders, occupied waiting berths, and orders with a dispatched HTM;
- for every presentation pair: inventory-ready ETA and actual time, order-ready ETA and actual time, selected APP, operator-ready time, predicted start, actual start, and the dominant wait at selection and at execution;
- time with operator idle while zero, one, or both sides are physically ready;
- preparation lead: berth-clear time minus successor order/container/source readiness;
- inventory sequence position and any time an earlier-ready source blocks a later source;
- direct/buffer path requested versus path actually used under an override, plus final-pick-to-APP-clear and final-pick-to-extraction intervals.

The current conveyance already exposes operator, presentation, conveyor, and retained-HTM occupancy plus committed transfers (`model/conveyance/mod.rs:419-463`). The missing observability is chiefly logical order state and the paired ETAs/reasons before a transfer exists. `OrderComplete` alone is too late, and completion-tracker registration is too dependent on stock reservation to stand in for assignment.

## Priority and defect classification

1. **Correct the 9s input to the newly confirmed 10s value** and preserve iteration 10's exact 9-second result as the named control. This is a known input defect.
2. **Add exact assignment/preparation/admission metrics and state transitions.** This is a known observability/modeling gap and is required to test the six-order saturation claim.
3. **Add the station coordinator and admission ledger, separating logical CONWIP from bounded physical station-footprint occupancy.** This is a known architecture gap; whether assignment or timed dispatch above six improves throughput is experimental.
4. **Add explicit source/order ETA pairing telemetry, then tune pairing while preserving physical conveyor order.** Poor matching is an inferred bottleneck, not yet a proven defect.
5. **Add a configurable force-direct dispatch policy for the isolation experiment.** This is a requested experiment control, not a claim that buffer flow is faulty.
6. **Only after those measurements, test `W+1`, `W+2`, and preparation-depth variants.** Do not add floor parking or physical queue cells.

No change is needed to create a `TransferItems` task, make the operator exclusive, or hold both presentations through the pick; those behaviors already exist in authoritative code. The likely useful work is to expose and split the states surrounding that correct physical transfer so the scheduler can prepare ahead without pretending logical assignment is a berth or an HTM.
