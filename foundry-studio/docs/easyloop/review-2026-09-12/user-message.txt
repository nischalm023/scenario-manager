There are a lot of different small changes I think we need to make. Here are my (very partial) notes:&#x20;
\- I think diving board access cells are wrong - the access cell is UNDER the diving board, not in front of it
\- We need to remove north<>south traversability from diving board cells - HTMs can only enter and back out of relay ("diving board") cells. And no turning/rotation is allowed inside diving board cells! (or really any other presentation cells for that matter, but I'm talking about relay/diving board cells here in particular.
\- contrary to the transcript, I think we can actually leave the open floor areas as-is for a bit longer because their actual HTM traversability is fine, but later this week we will want to tweak/reorganize them as discussed in the transcript.
\- Later next week (not the priority for now) We need to implement floor-driving VTM types (with aisle pinning for now, but we can , and ensure that that
\- I think we need to temporarily disable the order buffer flows and drive all order totes / boxes directly  from the easyloop stations to an extraction port. the point of this is to isolate our variables a bit, so we can eliminate any potential backpressure from the order buffer being full, or any fiddling with delayed order extraction timings
\- The thing I think we really need to focus on today is the easyloop station internals
&#x20; \- I don't think we're currently modeling the operator as a single exclusive resource, or the 10s pick as a task assigned to/that utilizes said operator. I believe we are using a fixed dwell time for the order HTM and inventory tote presentation, which is wrong
&#x20; \- We need to ensure that we are tracking the number of Orders assigned to an easyloop station, and ensure that (in the unconstrained order timing) it is constantly saturated. right now each easyloop station has 6 waiting cells, so there should always be 6 orders assigned to the easyloop station. This is a scheduler, so there should not be one single milisecond where fewer than 6 orders are assigned to an easyloop station, except at the very end when we might be out of orders. I think we need a time-series metric to help us visualize and confirm this
&#x20;   \- Should this actually be higher than the "W" value (6 in this case) to account for dispatch latency? how do we reason about congestion/deadlocks inside the easyloop station? Should we maybe assign more than W orders, and dispatch HTMs early (based on some conwip target) and only admit HTM's pertaining to W orders at a time? Need to game this out
&#x20; \- we need to ensure that we are orchestrating the presentation of the order HTM (which is carrying th order tote/box) and the inventory tote to the operator (I think Vinay called this the "APP" automated presentation point?), with the understanding that inventory totes are not resequencable as they're on a conveyor, but order HTMs are recequencable due to the non-conflicting structure of the waiting block, but the arrival times for each is different because they are at different distances from the order HTM presentation point
\- We need to implement two different heatmaps (initially targeting whole-run cumulative traffic, but later potentially being by some configurable period)
&#x20; \- The heatmap view needs to be switchable in the UI
&#x20; \- each cell in the heatmap should show its value on hover, using the appropriate units (duration or speed respectively)
&#x20; \- One of the heatmaps is total wait time per cell over the period (excluding queue cells and presentation/access cells, because they'll throw off the scale)
&#x20; \- The other heatmap is about average/median HTM speed. we anticipate that in a healthy flowing system, that there will be waves of higher speed traffic interspersed with lower speed crossing/turning traffic, and so it will likely be bimodal. I'm not sure of the best way to illustrate this, as there are different scenarios where that crossing/rotating traffic might congest the higher speed traffic waves, versus other cases where they are sufficiently separated in time. standard deviation? maybe there's a better way. either way we need to help people understand the traffic speeds.
