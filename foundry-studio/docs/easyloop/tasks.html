The implemented parent hierarchy

The Walmart JSON selects FulfillOrders after fleet, inventory and order setup. It creates presentation-owned order streams from a shared pending queue. Each stream stays on one side, while an area-admission calendar assigns one of that side's six waiting places when the order may enter. The root waits for picking and every outbound dispatch to finish.

Current scope: each EasyLoop has two independent six-member order areas, each bound to one fixed order presentation. Logical assignment ends at final pick; physical membership ends at actual area exit. Inventory queue travel, picking and return work overlap. The conveyance service independently enforces eight-tote physical capacity, two inventory presentations and one shared exclusive operator. Detailed physical FIFO and belt transfer conflicts remain further work.

Pipeline sizing: inventory CONWIP is ceil(queue_factor × F_max / pick_period) + 2, using a static retrieval-time estimate. It counts visits from release through paired pick completion. The logical stream ceiling uses this cap; the old half-fleet worker limit is removed. Actual relay and robot acceptance protects the resources needed to finish admitted work. Current supply prepares one active inventory visit per logical order. These are admission limits, not evidence of sustained operator saturation.

Diagnostics: typed events record exact simulation times for order assignment and physical phases, paired order/inventory readiness by order and pick index, and inventory visit release, load, conveyor boarding and pick completion. Desvis plots logical orders, physical residents and the shared inventory CONWIP/upstream/loaded-transit counts. Profiles without these events show the measurements as unavailable rather than zero.

Validation scope: focused workflow tests cover admission and diagnostics across direct and buffered routes. Full-map batches of 100 and 500 orders completed; the 500-order run exercised all four derived CONWIP ceilings. The matched eight-hour comparison completed 4,981 picks (622.625/hour), up 11.48%; site-capacity validation remains pending. See the implementation and validation record. Acquire the physical order container

Bag orders use a reusable Tote; SIOC orders use a reusable Tray. Both are retrieved from the matching empty-container pool. Box orders use a newly inducted Carton, carried directly on the HTM. These are the current provisional physical mappings. After assignment and stock reservation, the first inventory SupplyAndCollect is launched before the area right is awaited; order-container acquisition starts only after AdmitArea has accepted a possibly future entry time. This preparation-ahead behavior currently applies to inventory only. Supply includes pipeline admission, retrieval, delivery, conveyor admission, unloading and queue launch. The same independent child supplies only the next required inventory visit while an unfinished order returns to Waiting. The order parent coordinates presentation after receiving both the supplied tote and its order HTM; arrival alone does not transfer custody or permit a pick.

Creation occurs at the induction cell when the HTM is ready; pickup completes after the fork dwell. Dynamic creation metadata preserves the carton’s physical type in live and recorded playback. No packaging operation is added at EasyLoop.

Dispatch, extract, then release the physical resources

DispatchOrder owns the outbound container after the last pick. The current DS path stores and retrieves it through the order buffer; SC and 3P proceed directly to extraction. All paths retain the physical container type. Its Navigate child chooses among declared extraction ports at actual HTM readiness, reselecting after reservation changes when blocked. Normal collision planning still reserves the physical route.

Tote or tray: return the empty container

ExtractOrder removes the contents at the end of the extraction dwell. The reusable container remains on the HTM, and StoreTote returns it to OrderDepot for another order. After the relay reservation is committed, its HtmStore child can answer a blocked incoming journey's request to plan this known departure sooner. Extraction still receives its full dwell, and only the actual storage route bounds the source cell's hold. If the relay is occupied, that hold remains while other tasks can continue; the laden HTM never enters the idle pool for this decision.

Carton: remove the box and release the HTM

ExtractOrder removes the whole carton when the extraction ends. DispatchOrder registers the empty HTM and spawns its clearance, ClearPresentation: a last-resort claim on that availability, with a Vacate on the extraction cell's hold. A feasible published productive claim for that availability takes priority when it departs no later than the clearance, at the extraction's end; one that would depart later loses to the clearance. An incoming journey blocked at all eligible ports may register a need-by on that Vacate, so that its arrival can be planned before the extraction ends. This changes when the choice is made, not when the HTM can physically leave. Otherwise the accepted clearance parks the HTM: it finds and reserves an available relay presentation cell and route. An obsolete clearance dissolves before route planning. If an early accepted attempt has no available relay, it restores the availability and waits until the physical departure time before a fresh competition; productive work that departs then can take the HTM during that wait. If no relay is available at that retry either, the clearance competes again whenever a path commit may have freed one, until the barrier passes the extraction's end; then the run stops with an error naming the station, the HTM and that time. Other flows still use the existing pressure-relief mechanism.

Buffer timing is provisional: retrieval eligibility is stored_at + buffer_dwell, with zero dwell by default. Storage and retrieval still perform their real transport work. Source cutoff times do not schedule release; their meaning, DS/SC/3P routing and wave behavior remain site questions.

Further decomposition proposal: the next five trees retain the earlier design vocabulary. They describe potential extraction boundaries and are not a class inventory. Use the hierarchy above for implemented names and parentage.

The order tote stays with one parent

FulfillOrder owns the order’s tote through acquisition, repeated picks, and dispatch. For EasyLoop, the tote remains on the same HTM while it waits, presents, and circulates. The chosen side can change between picks.

One parent per task instance. A shared conveyor tote is a resource used by a pick. Its delivery task does not become a second parent of that pick. Resource dependencies are described separately under Scheduling.

The delivery HTM continues after deposit

SupplyAndCollectTotes is a reusable drop-and-collect composition: supply one tote, retain the robot, then collect an eligible tote from a configured return endpoint. EasyLoop binds its continuation to the one-way route under the conveyor.

Deposit splits custody. The conveyor resource takes the inventory tote. The task parent retains the empty HTM, its current hold, and its ready time. It never puts that robot back in the general availability pool while the configured continuation is unfinished.

AdvanceQueue owns a finite passage through a configured queue. A queue service chooses legal holding locations; actual movements use Navigate children. Waiting is a resource-signal wait with custody intact. A navigation cell does not automatically create a task.

A pick presents the totes, transfers items, and clears the presentations

PickItem owns one compatible reservation covering both tote placements, an operator interval, and clearance to the next safe holds. Its children consume those accepted reservations; they do not compete again for the same resources.

TransferItems names both tote IDs, the SKU, quantity, and operator reservation. Its item-transfer event takes effect at the end of the committed pick interval. Inventory and order progress must not report that work as physically completed at an earlier time.

Decompose at real scheduling and custody boundaries

A small task earns its place when it can be scheduled independently, moves a robot or shared mechanism, transfers custody, or produces a useful typed result. Selecting a candidate, waiting for a signal, and visiting each path cell remain operations within tasks and services.

Names describe responsibilities, not approved public Rust APIs. Extract only where the responsibility is real; do not require a pass-through wrapper around a single leaf. Reuse comes from explicit inputs and injected capabilities, not a new machine-type enum or a generic workflow language.

Use Butler’s vocabulary where the responsibilities match

Butler’s fulfillment code uses carrier for types including tote and packing_box. Its material-handling tasks use tote, load/unload, transport, presentation point, and waiting block. These diagrams use that concrete vocabulary. A tote is the container; the HTM is the robot carrying it. PPS means pick/put station.

Schedule one compatible pick window

Parentage does not make resources ready. Before committing a pick, the resource services must provide a compatible bounded plan for these conditions:

Claim Required condition Held until
Inventory presentation The chosen inventory tote is at the selected position with the requested items available. The tote clears, or a subsequent accepted pick retains its occupancy.
Order presentation The correct order tote and its HTM are present on the matching side. The HTM completes its curved departure to the next safe hold.
Operator The shared operator is free for the transfer interval; both tote placements are ready. The committed item-transfer interval ends.
Clearance The plan can continue to safe holding locations after the pick. Those movements finish and successor holds take ownership. 
pick_start = max(inventory_ready, order_ready, operator_ready)
pick_end   = pick_start + transfer_duration

The accepted plan must keep both presentations occupied through pick_end.
The operator frees at pick_end; each tote hold frees when that tote clears.

V2 provides the scheduling contract

Tasks propose revocable candidacies, acceptance converts them into held reservations, and scheduling consumes them. Parents create children through SchedCtx::add_task and pass typed handoffs. The scheduler remains unaware of EasyLoop.

A child’s returned schedule may describe future work. Successors must use its ready time and reservation; awaiting the Rust future does not mean the settled simulation clock has reached that time.

Wait without blocking unrelated work

Do not publish an inadmissible earliest proposal whose prerequisite requires another task to be accepted. That can pin the trailing global barrier. Wait locally on resource version changes, re-quote, and publish a startable candidacy.

A bad route or impossible transfer is an error. An occupied but eventually available resource is a wait. Cancellation must drop tentative claims and preserve or reconcile already committed custody.

The conveyor owns one shared physical schedule

At deposit, a conveyor-held tote becomes available to compatible pick proposals. Its capacity claim lasts through presentation and return until collection. Tote position requests use the shared conveyor service: a main-belt movement affects all riders, and side transfers can reorder totes only where the declared mechanism allows it. Independent per-tote timers are insufficient.

Initially, model meaningful moves, stops, side transfers, and occupancy. Detailed roller physics can wait. Later tote animation reads these committed events and their effective times, including pauses for picking; it must not invent its own route or timing.

Compositions select roots; tasks resolve shared state

Named compositions now live in a JSON-only folder: cencora.json and walmart.json. A scenario selects "composition": "walmart", or supplies an inline {"tasks": [...]} definition. The default is cencora; Walmart specs select their own composition explicitly.

The hardcoded fn cencora and ModelState are removed. Cencora selects its pick, putaway and return families. Walmart selects FulfillOrders; its children perform physical conveyor handling, picking and outbound dispatch.

Composition format, manager lifecycle and validation

Working sequence before throughput and animation

FillInventory preloads the full on-hand snapshot before orders run. Automatic placement balances total units among inventory totes, preserving all SKU quantities and allowing mixed contents. The full Walmart map receives 1,397,589 source units plus an explicit, approved 43-unit demo top-up in 162,060 totes (8 or 9 units each); limiting order count does not reduce that stock. Vinay’s tote-addressed mock-put file will supply actual placement later. See preload details.

The implementation transfers real stock from the inventory tote into the order’s tote, tray or carton at the end of the paired pick dwell. Both containers must remain correctly presented throughout that dwell, and the shared operator cannot serve overlapping picks. The order HTM can circulate and change presentation sides between picks.

An order returns to the waiting block only when it still needs another pick. After its final pick, its existing HTM continues toward buffer storage or extraction from the presentation. Its waiting-space allocation becomes reusable after that pick and physical clearance of its last waiting-cell reservation; downstream work retains its own robot and cell reservations. Outbound congestion can still delay physical departure, but a completed order is not deliberately parked in the sequencing block.

The inventory HTM unloads its tote, traverses every cell of the one-way queue, and stays retained until a returning tote is collected. Conveyor admission and collection hold physical capacity through their actual handoff times. The HTM at the queue head takes the earliest ready returning tote. This can differ from its original delivery: presentation sequencing can change the tote return order, while HTMs cannot overtake in their queue.

Curved robot links use the same committed geometry and kinematic timing in Ghost and collision modes. Conveyor totes now animate along recorded inbound and return intervals, including their contents and inclination. Detailed main-belt sequencing remains future work: the current flow uses declared transit timing and does not yet model every stop and lateral shift of a populated main belt.

Geometry remains at the reviewed checkpoint. The broader world-protocol format migration and unresolved worldlens decisions remain parked. Separating Cencora's roots and passing focused regressions does not establish full historical Cencora parity.
